## 5. 기술 설계 (요약)
- **서버가 결정한다:** 대여와 만료는 모두 서버 시계 기준이다. 클라이언트는 표시만 한다
- **선착순 동시성:** SQLite **한 트랜잭션 안에서** "재고 확인 → 1 감소 → 대여 기록"을 처리한다 (`BEGIN IMMEDIATE`). 같은 순간 두 사람이 눌러도 재고가 넘치지 않는다
- **DB 테이블**
  - `shop_items`: 소품 정의 (id, 이름, 착용 위치, 하루 수량, 사용 시간, 공개 시간대, 판매 기간)
  - `shop_stock`: (날짜, 소품, 시간대) → 남은 수량
  - `rentals`: (사용자, 소품, 시작, 만료, 반납 여부)
- **동기화:** 착용 중인 소품을 `PlayerInfo`에 실어 보내고, 만료되면 서버가 모두에게 알린다
- **3D:** M8에서 만드는 캐릭터에 **손, 머리, 등, 어깨 부착 위치**를 추가한다. 소품은 저폴리 기본 도형으로 만든다
- **보안과 남용 방지:** 대여 API 횟수 제한, 출처(Origin) 확인, 동의 확인, 계정당 하루 제한. 새로 만든 계정의 첫날 제한도 검토
- **계정 탈퇴와 내보내기:** 대여 기록을 포함한다
- **관리자:** 소품 수량과 공개 시간을 조정하고, 오늘 대여 현황을 본다 (M8의 관리자 권한을 재사용)


### 5-1. 멱등성 설계 (필수)
- **대여 요청마다 고유 키:** 클라이언트가 버튼을 누를 때 `requestId`(UUID)를 만들고, 재시도할 때도 같은 키를 쓴다
- **서버:** `rentals(request_id UNIQUE)`. 같은 키가 다시 오면 **새로 빌리지 않고 처음 결과를 그대로** 돌려준다 (성공이든 품절이든)
- **한 트랜잭션:** 재고 감소, 하루 횟수 증가, 대여 기록을 `BEGIN IMMEDIATE`로 묶는다. 중간에 실패하면 전부 되돌린다
- **같은 소품 중복 대여 금지:** `(user, item, 활성)`에 유일 조건을 걸어 두 번 눌러도 1개만 빌려진다
- **반납과 만료도 멱등:** 이미 반납했거나 만료된 대여에 다시 요청하면 "이미 처리됨"으로 성공 응답하고, 상태는 바꾸지 않는다
- **만료 처리:** 서버 재시작이나 중복 실행에도 안전하게 `UPDATE ... WHERE status='active' AND ends_at<=now` 한 번으로 처리한다
- **시간대 재고 생성:** `INSERT OR IGNORE (date, window, item)` 방식이라 몇 번을 실행해도 재고가 한 번만 만들어진다
- **클라이언트:** 응답을 받기 전에는 버튼을 잠그고, 연결이 끊겼다 다시 이어지면 서버 상태를 다시 받아 화면을 맞춘다 (화면이 상태를 추측하지 않음)

## 6. 법과 정책 체크
- **무료, 결제 없음:** 전자상거래와 청약철회 문제가 없다
- **확률형 뽑기 없음:** 게임산업법의 확률형 아이템 규제 대상이 아니다
- 나중에 **유료화하거나 포인트를 사고팔게 되면** 별도 검토가 필요하다
- 개인정보처리방침에 "대여 기록" 항목을 추가한다 (보관 기간 예: 30일)

## 7. 나중에 붙일 수 있는 것 (2단계)
- **QT 달란트:** 묵상 작성, 연속 QT 같은 활동으로 받는 무료 포인트로 **추가 대여권**을 얻는다. 신앙 활동을 보상하는 구조라서, "점수 때문에 QT 한다"는 부작용이 없는지 신중히 검토한다
- **빈자리 알림:** 다음 공개 시간에 알림을 받는다
- **모임 소품:** 모임 단위로 함께 쓰는 소품 (예: 모임 깃발)
- **선물하기:** 내 대여권을 친구에게 준다
